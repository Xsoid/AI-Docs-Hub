# Качество Ранжирования Поиска

## Что Изменилось

- Score - BM25 (`k1 = 1.2`, `b = 0.75`) вместо TF-IDF без нормализации по длине chunk. Backend и раньше назывался `lite-json-bm25`.
- Вес по типу источника: tests, test-скрипты, changelog и `docs/changes/` - `0.6`; ADR/decisions, architecture, `AGENTS.md`, `CLAUDE.md`, README - `1.25`. Вес виден в поле `source_weight`.
- Каждый файл представлен в выдаче одним лучшим chunk.
- При равном score порядок определяет `source_path`.
- `search_docs`, `search_decisions` и `search_modules` принимают optional `min_confidence`. По умолчанию результаты не отсекаются.
- Набор оценки: synthetic-проект `tests/fixtures/search-eval/` с 10 запросами и метриками MRR и recall@5 по различным файлам.

## Почему

Ручная проверка показала дубли одного файла в выдаче, тестовые скрипты выше ADR и массовые ничьи без связи с важностью документа.

## Результат

| Метрика | До | После |
| --- | --- | --- |
| MRR | 0.717 | 0.9 |
| recall@5 | 0.8 | 0.9 |
| Повторы файла в top-8 | 12 | 0 |

- Без веса по типу MRR падает до 0.8: тестовый скрипт и change note снова занимают первое место.
- Нормализация по длине на этом наборе метрику не меняет. Кейс с длинным chunk в fixture не воспроизводится.
- Оставшийся промах - запрос на английском по документации на русском. Ранжирование его не решает.

На индексах шести подключенных проектов (18 запросов): повторов файла было 28, стало 0; первый результат сменился в 4 запросах.

## Эксплуатация

- Переиндексация не нужна: веса считаются при поиске.
- Шкала `confidence` изменилась. Средний `confidence` первого результата на подключенных проектах: 0.654 до, 0.57 после. Порог `min_confidence` выбирайте по новой шкале.
- Правила описаны в `docs/standards/rag-policy.md`, раздел «Ранжирование».

## Проверка

```sh
python3.11 -m tests.search_eval
```

## Follow-Up

Переопределение весов через project config не реализовано. Его стоит добавить, когда понадобится проекту с нестандартной структурой.
